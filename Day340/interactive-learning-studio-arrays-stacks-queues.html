MODULE 01 / FOUNDATION

Arrays — Contiguous Memory

Everything a stack or queue can do, an array can be made to do underneath. Start here to understand the ground floor.

Explanation core idea

An array is a block of memory cells sitting right next to each other, each the same size, each reachable by an index. If the array starts at address 0x1000 and each element is 4 bytes, element i lives at 0x1000 + i × 4. That formula is the entire trick — no searching, no walking pointers. That's why arr[7] is O(1): it's arithmetic, not a search.

Fixed-size arrays reserve that block once. Dynamic arrays (JS arrays, Python lists, C++ vector) fake resizability by allocating a bigger block and copying everything over when they run out of room.

// address of arr[i] address(i) = base + i * elementSize // example: 4-byte ints, base 0x1000 arr[0] → 0x1000 arr[1] → 0x1004 arr[2] → 0x1008

Analogy

Think of a row of numbered lockers bolted to one wall, all identical size. If you know the locker number, you walk straight to it — no need to check every locker before it. But if the row is full and a new locker needs to fit, you can't just wedge one in — you need a whole new, longer wall, and every locker's contents gets carried over.

Exercise

Predict the output

Given arr = [10, 20, 30], what does arr look like after arr.splice(1, 0, 99)? Write your answer, then reveal.

Reveal answer

Common misconceptions

"Arrays can always grow for free." Dynamic arrays only feel free — under the hood, growing past capacity means allocating a new block and copying every element, an O(n) operation that just happens rarely enough to average out.
"Index 0 is just a convention." It's the direct result of the address formula — base + 0 × size is the base address itself. Indexing from 0 isn't a style choice, it falls out of the memory math.

Key takeaways

  • Arrays trade flexibility for speed: O(1) reads because position is pure arithmetic.
  • Inserting or deleting anywhere but the end costs O(n) because elements must shift.
  • "Dynamic" arrays are fixed arrays that secretly reallocate and copy when full.

MODULE 02 / APPLICATION

Stacks — Last In, First Out

Restrict an array to two operations at one end only, and you get a stack — a structure that quietly runs your function calls, your undo button, and your browser's back arrow.

Explanation

A stack only allows two moves: push (add to the top) and pop (remove from the top). Nothing else is reachable directly — you can't grab the third item from the top without first popping the two above it. That discipline is the whole point: it enforces an order guarantee, Last In, First Out (LIFO).

Every function call in every programming language uses a call stack: when function A calls B, B is pushed on top; when B returns, it's popped, and control resumes exactly where A left off.

class Stack { items = [] push(v) { items.push(v) } // O(1) pop() { return items.pop() } // O(1) peek() { return items.at(-1) } }

Analogy

A stack of plates in a cafeteria spring-loader. You can only take the top plate, and you can only add a plate to the top. To reach the fifth plate down, you'd have to remove four plates first — the structure physically prevents any other order.

Try it interactive

Push a few values, then pop — notice the last one pushed is always the first one popped.

Exercise

Trace the call stack

Given f() calls g(), which calls h() — list the order frames are popped as each function returns.

Reveal answer
Push order: f → g → h Pop order: h → g → f // h finishes first because it's on top — the last one pushed

Common misconceptions

"A stack is a totally different structure from an array." Most stacks are literally an array underneath, with a rule bolted on: only touch the last index. The restriction is the feature.
"Stack overflow means the stack is 'full'." It means recursion or nesting went too deep for the memory reserved for the call stack — usually a missing base case, not a capacity problem to fix by allocating more.

Key takeaways

  • Stacks enforce LIFO by only exposing the top of an underlying array or list.
  • Push and pop are both O(1) — no shifting, because only the end ever changes.
  • Recursion, undo history, and expression parsing all lean on this exact structure.

MODULE 03 / APPLICATION

Queues — First In, First Out

Flip the restriction to the other end and you get fairness instead of urgency: whoever arrived first gets served first.

Explanation

A queue allows enqueue at the back and dequeue from the front — First In, First Out (FIFO). Printers, task schedulers, and message brokers all use this shape because it guarantees order of arrival is preserved.

Naively removing from the front of an array is O(n) — everything shifts left. Real implementations use a circular buffer (two pointers, front and back, wrapping around a fixed block) so both ends stay O(1).

class Queue { items = [] enqueue(v){ items.push(v) } // back, O(1) dequeue() { return items.shift() } // front, O(n) naive } // circular buffer avoids the O(n) shift using front/back indices

Analogy

A coffee shop line. New customers join at the back; the barista only serves the person at the front. No cutting — whoever waited longest is served next. A circular queue is that same line wrapped around a roundabout: once the last seat is freed at the front, a new customer can loop around to fill it, instead of the whole line shuffling forward.

Try it interactive

Enqueue a few values — dequeue always removes from the front (leftmost), never the back.

Exercise

Spot the bug

A print queue implementation calls items.pop() instead of items.shift() to remove the next job. What breaks?

Reveal answer
// pop() removes from the END (LIFO behavior) // but a queue must remove from the FRONT (FIFO) // result: the most recently added job prints first — // jobs submitted earlier get stuck waiting indefinitely

Common misconceptions

"Queue and stack are interchangeable if I just track two ends." The end you remove from is what defines the guarantee. Swap it and FIFO silently becomes LIFO — often the hardest kind of bug to spot because it "looks" like it's queuing.
"Array.shift() is fine for a queue." It works correctly but is O(n) per call in most languages, since every remaining element must shift left — a circular buffer or linked list avoids that cost.

Key takeaways

  • Queues guarantee FIFO by restricting insertion to the back and removal to the front.
  • Naive array queues cost O(n) to dequeue; circular buffers keep it O(1).
  • A deque generalizes both stack and queue by allowing either end to be used.

MODULE 04 / MASTERY

Choosing & Combining Structures

Real problems rarely announce which structure to use. This module builds the judgment to choose fast, plus two classic problems that combine everything so far.

Explanation

The decision usually comes down to one question: what access pattern does the problem demand?

  • Need any element by position, often? → Array.
  • Need to undo the most recent action, or match nested pairs? → Stack.
  • Need to process things in the order they arrived? → Queue.

Worked example 1 stack

Validating balanced brackets like "{[()]}" — the classic proof that stacks understand nesting.

function isValid(s) { const stack = []; const pairs = { ')': '(', ']': '[', '}': '{' }; for (const ch of s) { if (!pairs[ch]) stack.push(ch); // opening bracket else if (stack.pop() !== pairs[ch]) return false; // mismatch } return stack.length === 0; }

Every opening bracket is pushed; every closing bracket must match whatever is currently on top. If it doesn't, the nesting is broken — a direct use of LIFO order.

Worked example 2 queue via two stacks

A classic interview twist: build a FIFO queue using only two LIFO stacks.

class QueueFromStacks { inStack = []; outStack = []; enqueue(v) { inStack.push(v) } dequeue() { if (outStack.length === 0) while (inStack.length) outStack.push(inStack.pop()); return outStack.pop(); } } // reversing into outStack twice restores original arrival order

Practical exercise

Design decision

A ride-share app needs to match the longest-waiting driver to the next request, but also let a driver cancel and re-add themselves to the very front if a trip falls through last-minute. Which single structure fits best, and why?

Reveal answer
// A DEQUE (double-ended queue). // Normal matching = dequeue from the front (FIFO fairness). // Re-adding to the front after a cancelled trip needs // insertion at the front too — something a plain queue // can't do without breaking its own invariant.

Common misconceptions

"More advanced structures (trees, graphs) replace these." Trees and graphs are usually built from arrays, stacks, and queues — tree traversal is a queue (BFS) or a stack (DFS) in disguise.

Key takeaways

  • Choose by access pattern: random access → array, nesting/undo → stack, arrival order → queue.
  • Stacks and queues are usually thin behavioral wrappers over an array or linked list.
  • A deque combines both when a problem needs flexibility at either end.

Practical Challenge & Continued Learning

Final challenge

Implement a "min-stack": a stack that supports push, pop, and a getMin() that returns the current minimum — all in O(1). Hint: an ordinary stack combined with a second stack that tracks running minimums solves this without scanning.

Reveal one working approach
class MinStack { stack = []; minStack = []; push(v) { stack.push(v); const currentMin = minStack.length ? Math.min(v, minStack.at(-1)) : v; minStack.push(currentMin); } pop() { stack.pop(); minStack.pop(); } getMin() { return minStack.at(-1); } }

ARRAY

index(i) = base + i*size read: O(1) insert@end: O(1)* insert@front: O(n)

STACK (LIFO)

push() → top pop() ← top peek() = top, no removal

QUEUE (FIFO)

enqueue() → back dequeue() ← front circular buffer = O(1) both ends

WHEN TO USE

random access → array undo / nesting → stack arrival order → queue either end → deque
