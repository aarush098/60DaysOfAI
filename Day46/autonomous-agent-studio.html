Architecture overview

How the loop works

Planner produces a build spec once. Executor writes the first draft. Then, each round: Evaluator scores the current draft against the rubric with a live API call, Critic finds concrete flaws from that score, and Improver rewrites the draft using both. The new draft feeds the next Evaluator call — a real cycle, not a fixed script.

How the stop-check governs flow

After every Evaluator call the app checks, in order: plateau (score gain < Δ for 2 rounds straight), threshold (score ≥ target), then hard cap. Whichever fires first ends the loop and hands the latest draft to the Final Reviewer, which never sees an unscored draft.

Memory across rounds

The Memory Manager doesn't call the model — it condenses each round's score/critique into a running log that is threaded into every subsequent Improver prompt, so revisions don't repeat fixes or regress on earlier feedback.

Extension ideas

Parallel evaluators

Run 3 Evaluator calls with different rubric weightings (a11y-heavy, perf-heavy, DX-heavy) and average their scores for a more robust signal per round.

Tool-using Executor

Give the Executor a sandboxed code-execution tool so it can actually run the component's JS and catch runtime errors before the Evaluator ever sees them.

Human-in-the-loop gate

Insert an approval step before Final Reviewer publishes — surface the draft and let a person accept, request another round, or override the stop condition.

Cross-task memory

Persist the Memory Manager's condensed lessons across separate runs, so future component builds start with house-style conventions already learned.

Cost/latency budget

Add a token-and-time budget the Safety Monitor enforces alongside the iteration cap, stopping early if a round is about to blow the budget.

Multi-artifact orchestration

Generalize Planner to split a brief into several components, run one loop per component concurrently, then have Final Reviewer check they compose together.
