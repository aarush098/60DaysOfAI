The system prompt design

The tutor runs on a single system prompt with a strict role, scope, and output contract, sent with every call to claude-sonnet-4-6:

  • Role: a warm, patient teacher — never condescending, never a wall of jargon. Explanations always include a concrete analogy, because analogies are what make abstract concepts "click."
  • Scope: restricted to educational explanation. Off-topic requests (homework answers with no learning value, unrelated chit-chat, anything harmful) get redirected back to "what would you like to understand?" rather than refused abruptly.
  • Output contract: the model is instructed to return strict JSON with fixed fields (topic, teacherNote, explanationHtml, quiz) so the UI can render each part into its own visual slot — no regex-parsing of freeform prose.
  • Edge cases: if the input is too vague ("explain it"), the model asks one clarifying question instead of guessing. If pasted text or an uploaded file isn't actually educational content, it says so plainly rather than inventing a lesson.

Why the UI looks like this

A concept tutor's whole job is making abstract ideas feel concrete, so the interface borrows straight from a real study session: a chalkboard where you ask the question, and a sheet of paper where the answer lands — quizzes appear as flashcards you flip through one at a time, mirroring how a tutor would actually check your understanding rather than dumping every question on screen at once.

How to extend it

  • Memory: track topics covered in a session array and pass a short "what we've covered so far" summary into the system prompt, so the tutor can build on earlier explanations instead of starting fresh each time.
  • Tools: add the web_search tool to the API call for topics that need current facts (e.g. recent scientific findings), and let the model cite sources in the explanation.
  • Multi-step flows: turn the single quiz round into a mastery loop — if the student misses a question, automatically request one more targeted explanation + a follow-up question on just that sub-concept before moving on.
  • File support: this build reads plain text (.txt/.md) via FileReader. For PDFs or Word docs, send the base64 file as a document content block in the API request instead of extracting text client-side.
